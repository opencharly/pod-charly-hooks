# 2026.332.1342 — feat(marketplace)!: delete the jupyter family declaration

## Summary

`pod-charly-hooks` owns the ONE `marketplace:` entity, whose `families:` map is the single family registry the corpus generator refuses an undeclared skill against. It declares 45 families today, one of them `jupyter`.

`pod-charly-hooks#23` deleted the jupyter catalogue entry with the retired Jupyter image family. `#24` restored the bare family name for one measured reason: `layer-llama-cpp` still declared `skill.llama-cpp.family: jupyter`, so no generation could pass without it. The operator has since ruled that llama.cpp "should have never been in the jupyter family in the first place" and chose `ollama`; `opencharly/layer-llama-cpp` moves the skill there, so the `jupyter` declaration now has no member and is dead (D-LAW-2).

This PR deletes exactly that declaration: five lines, one file. `ollama` and every other family entry are untouched.

This is the second producer leg. `opencharly/layer-llama-cpp#8` has ALREADY merged (`d9e7a3a11c127bd78f4984f076e60ab7ec84c9ed`, tag `v2026.332.1333`), so the move this deletion depends on is in place; W6's corpus regeneration pins this repo at THIS PR's tag, not at `v2026.332.1301`.

The regeneration also needs two measured things this repo cannot supply: `retired_skills: ["jupyter/llama-cpp"]` in `retired.cue` (a stale `layer-llama-cpp:v2026.272.0321` pin still reaches the pre-move card, which the dedupe key cannot merge with the moved one — `opencharly/plugin-marketplace#71`), and `git rm -r -- jupyter` (the generator prunes only families that still exist). The full-corpus run under `## How tested` carries both.

Relates to `opencharly/opencharly#1355` (W10).

Two things this run measured that the move alone does not fix, and both are reported to the marketplace leg (W6) rather than worked around here:

1. **A stale pin resurrects the pre-move card.** `layer-python-ml` still pins `layer-llama-cpp:v2026.272.0321`, and an old `layer-python-ml` tag (`v2026.290.1914`) is itself in the closure, so the pre-move `family: jupyter` copy is fetched anyway. The generator's dedupe key is `{kind, family, name}` (`resolve.go`), so the moved copy and the stale copy are DISTINCT entities and the stale one is refused against the deleted family. Suppressing the retired CARD (`retired_skills: ["jupyter/llama-cpp"]`) makes the run pass; filed as `opencharly/plugin-marketplace#71`.
2. **The generator never prunes a family that no longer exists.** `scanGenerated` walks only the CURRENT families, so `jupyter/` is removed explicitly (`git rm -r -- jupyter`) in the marketplace leg; a regeneration does not recreate it afterwards, which the run above measures.
